# The new save in the normal maps

From stage ATG the 1.29.2 map saves with the same FSVB code as the native Reforged
Forsaken line (experiments/Forsaken). Reforged gameplay uses Forsaken EI; the normal
Reforged outputs are only authoring intermediates for the 1.29.2 conversion. Codes and files are the same in
every map, so a save made in one loads in the others. `SAVE_ENABLED` in SaveSlots.j switches it.

## Commands

| Command | What it does |
|---|---|
| `-save` | Shows the new code as numbered `-load FSVB:...` lines to screenshot; `-savepage N` shows page N |
| `-savef` / `-savef NAME` | Writes the code to `Documents\Warcraft III\CustomMapData\FFERPG\Last save.txt` / `NAME.txt` |
| `-load` / `-loadf NAME` | Loads `Last save.txt` / `NAME.txt`, new format or old |
| `-load FSVB:...` | Loads the code from its numbered chat lines, in any order; `-loadstatus` lists missing parts |
| `-load <old code>` | Old codes still load through the old loader |
| `-newcleanup` | Clears a failed load that could not tidy up by itself, so you can load again |

Messages say only whether a save or load worked and, if not, why. Since ATL the wording lives in
the Reforged save sources themselves, so the Forsaken maps say the same once rebuilt.

## Difficulty

| Game | Loads saves made in |
|---|---|
| Simple, Easy, Normal, Hard | Simple to Hard, and Inferno |
| Inferno | Inferno only |
| Nightmare | any difficulty |

Nightmare preserves the imported save tier when saving again: Easy to Nightmare to Easy
works, but Easy to Nightmare to Inferno fails. Inferno to Nightmare saves remain loadable
anywhere. A fresh Nightmare character has top-tier eligibility. Outside Nightmare, saves
use the current game's tier (Inferno loaded and saved in Easy becomes an Easy-tier save).
Old-format imports retain their original tier in Nightmare too.

## How it is connected

- `src/triggers/12 Save system/` holds the eight save modules, generated by
  `python tools/save_port.py <built map>` from the Reforged sources in experiments/Forsaken. The
  tool never edits those. Codec, item life, cache and transport are copied unchanged; capture,
  load plan, object creation and loader differ only where they ask a hero's Reforged bag or
  equipment slots where an item is. Each change is an exact match the tool checks, so a change
  to the Reforged sources that breaks the port stops the tool instead of guessing.
- `SaveSlots.j` (TSaveSlots) answers those questions from the backpack pages.
- `SAVE_NEW_FORMAT` in SaveSlots.j is false in the Reforged map. `tools/save_legacy.py` switches it on
  when the build makes the 1.29.2 map, in the same step that moves the transport onto the game cache.

## Positions (the same in both versions)

| Save position | Reforged | 1.29.2 |
|---|---|---|
| 0-5 | hero quick slots | hero quick slots |
| 6-35 | 30-slot bag | backpack pages 3-7 (bag slot n = page 3 + n/6, slot n mod 6 + 1) |
| 36 helm, 37 chest, 38 gloves, 39 boots | equipment | page 1 slots 3, 4, 5, 6 |
| 40, 41 rings | equipment | page 2 slots 1, 2 |
| 42 weapon, 43 offhand | equipment | page 1 slots 1, 2 |
| 44 trinket | equipment | page 2 slot 3 |
| 45-50 / 51-56 | Gaya / house | Gaya / house |

Saving reads worn gear by its kind, wherever on page 1 or 2 it sits. A save stops with a message
if two worn items claim one position (for example two helms on page 1 before the page check has
moved one); move one to the bag and save again. A load puts each item in the slot above and
remembers the position, so the check after a load reads back exactly.

## Between versions

- A code or file saved in Reforged (DW and later) loads in 1.29.2 and the other way round: the same
  permanent item and job IDs, positions and account check. Decoding the Reforged files in
  CustomMapData shows every item has a place on the pages above.
- The account check uses the player name with any BattleTag number removed. A save loads only
  for a player whose 1.29.2 name matches that Reforged name.
- Difficulty follows the table above; Speedrun mode must match the game, as in Reforged.
- A weapon worn in the offhand (Dual Wield) loads as the second weapon on page 1. The page
  check then applies the wearing rules (BACKPACK.md): without Dual Wield it moves to the bag.
- Both versions use the same CustomMapData\FFERPG folder. If 1.29.2 cannot read a file, enable
  "Allow Local Files" (the `Allow Local Files.txt` helper in that folder does it); chat codes never
  need it.
- 1.29.2 cannot read an item's "can be dropped" flag. Every saved item is droppable by default;
  the loader remembers any it makes undroppable.

## Classic collection display (ATN)

Chronicle and Armory tooltips now use explicit one-based classic levels. Check their
collection totals in game. `-chronicle` lists every Chronicle category and the total;
`-armory` lists top-level Armory categories and the total stored collection.
`-equipment` lists all nine equipment slots, including empty slots; gear is managed
through the two equipment pages. Reforged retains the native Forsaken UI.

## ATO autosave and collection details

Autosave uses the same read-only full capture/file export as `-savef autosave`, and
skips busy or locked loads/saves and Hardcore games. Retest that all backpack pages
and items survive, then load the autosave file. Successful eligible loads announce
`-newgameplus` and enable its existing command, without granting new eligibility.
Secrets now shows its completion total and `-chronicle` calls that category Secrets.
The house Armory tooltip lists main categories; each open menu's Back tooltip
lists that category and its children, such as Physical Weapons and Tools.

## Runtime string isolation probe

ATS-StringProbe is a separate diagnostic, not the next gameplay build. Start a fresh
character without importing, type -checkpointstrings once, then create a new menu
save, fully exit Warcraft, restart and load it. The command builds one 1,500-character
string; no hero, inventory or progression state changes. Its source stays outside
the normal module list. The builder checks playable/editor compilation, startup,
archive preservation and identical converted gameplay object data against ATS.

Tiny's file is short; failed endgame checkpoints contain much longer dynamic code
strings. The user reproduced the unavailable/corrupted-save error and subsequent
crash with the fresh-character probe. The diagnostic container decompresses
completely and contains the intended long test string. This isolates long runtime strings from
imported items, job state and inventory handles. A 1 KB buffer in the classic
script-restoration path supports that diagnosis; it does not establish every
client's exact internal limit.

ATT / Forsaken EG keep new-format codes in immutable fragments of
at most 960 characters, including intermediate concatenations and substrings.
The logical codec remains the format specification; tools/save_strings.py lowers
its runtime/editor copies for both clients. The independent reference vectors,
file bytes, transfer packets, screenshot parts and permanent IDs stay unchanged.
The fragment table is allocated globally before local file IO, so reading a file
does not create a client-local handle. Numeric expressions keep their meaning.
Long-profile codec, file, delivery, screenshot and full load/recapture models pass;
Warcraft menu checkpoint acceptance still requires a new in-game test.

Legacy E/F/G/H imports keep their original dispatcher. Old preload files can
already contain a whole native code string; that legacy path retains its native
checkpoint limitation. This candidate targets new-format FSVB files, including
the tested endgame file. Earlier failed Warcraft saved games embed the old map
and cannot test the fix. Start a new game on the candidate, import an FSVB file,
create a new menu save, fully exit Warcraft, then restart and load that new save.

Validation: run `python experiments/Forsaken/test_save_strings.py` for the bounded
runtime codec, file, screenshot, both delivery paths and full load/recapture models.
The normal build gates also compile runtime/editor sources, check legacy save
compatibility and enforce source/runtime agreement.

## Bounded validation work after ATT

The user reported -loadf dev stayed on Loading for over a minute in 1.29.2 ATT.
The earlier model verified data but did not model Warcraft's per-thread execution
budget. ATU / Forsaken EI scan only 128 native characters per ExecuteFunc
child thread; individual varints and sections also have isolated execution budgets.
Completion flags make an interrupted child fail validation instead of leaving a
partial result accepted. Game-cache packets are already short, so their original
native string operations are retained. Cache catch-up drains one packet per player
per tick, and the transfer deadline is checked before decoding any waiting packet.

The loader also imposes a validation deadline. An interrupted preflight clears its
scratch state and allows another attempt. If character creation had started, it
uses the existing verified rollback; an owned capture writer is released as well.
The work-ceiling model is a regression check, not an emulator of Warcraft's exact
bytecode counter. In-game import and a new native checkpoint still need acceptance.

## Multiplayer local-file storage

The user reported long-save imports desynchronizing Forsaken/Reforged clients
during Loading. The earlier bounded-string implementation allocated local file
assembly into the same `FSS_Store` / `FSS_Next` used by synchronized decode. Only
the owner reads the file, so subsequent shared virtual IDs and table contents
could differ between clients. This is a synchronization risk; a model cannot prove
it is the only engine desync cause.
The PAIR004 implementation reproduces a shared counter of 5 on the file owner
versus 0 on an observer after the same requested long import in the two-client model.

The candidate uses an independently preallocated local table/counter and `!FL:`
references for file assembly. Shared decode retains `!FS:` references. Allocation
mode is explicit in local concatenation and follows the input for substrings;
there is no temporary global mode flag to leak if a VM thread is interrupted.
Only native packet text crosses the wire. FSVB bytes, file names, item/job IDs,
packet framing and checksums remain unchanged. The paired builder refreshes this
reviewed runtime support in existing editor references without changing the master.

The two-client model imports different long profiles concurrently and checks
identical shared fragment IDs/table state after every delivery. Export/readback
also preserves the same shared state on owner and observer. These tests pass;
multiplayer engine acceptance and the separate classic checkpoint fix remain pending.

For classic checkpoint isolation, `release/diagnostics/CheckpointNoItems.txt`
is a separately named copy of the user's dev file with only inventory section 1
replaced by an empty inventory. All other sections and account binding are retained;
the reference codec, actual JASS validator and detached load planner accept it. The copy remains over the
fragment threshold, so it still exercises bounded strings. Its report records the
source hash. It is also installed under the same name in CustomMapData/FFERPG;
the original dev.txt is unchanged. In a fresh classic game, use
`-loadf CheckpointNoItems`, make a new menu checkpoint, fully exit/restart, then
load it. Compare with a regular dev checkpoint made on the same candidate. Missing
carried/equipped gear is intentional in this diagnostic, not a load regression.

## PAIR007 multiplayer rejection and private IO boundary follow-up

The user reproduced a Forsaken PAIR007 desync with `-loadf dev`. The retained
2026-10-15 16.22.42 report identifies PAIR007, seven human players and turn 2018.
The associated replay contains the command but no following FSCU save-transfer
packet for that request. An earlier player's missing-file attempt did record its
FSCU X packet. This narrows the observed failure to private preparation/first send;
it does not identify an engine instruction or prove a unique root cause.

PAIR007 separated fragment IDs but still called FSS_Scan/ExecuteFunc from local
file alphabet checks, checksums, request validation and first-header preparation.
Those calls changed the same scan globals used by synchronized decoding. PAIR010
removes those private calls. The reader checks only bounded file framing/length,
retains the file header checksum as local metadata, and sends native packet text.
Alphabet, complete checksum, account, schema and profile checks run on every
receiver before the character can be changed. Export checksums are calculated on
every client before entering local file writing/readback. Legacy files have no
header checksum, so their sender computes it in bounded 128-character steps using
only private accumulator arrays; final legacy validation remains synchronized.

The canonical transport and paired-builder runtime refresh carry this change into
both profiles without modifying the user's editor master or native/classic sync
adapters. FSVB, file contents, filenames and wire framing are unchanged. Progress
messages identify synchronized transfer start and profile validation. The private
reader intentionally no longer serves as a content validator on its own.

Regression coverage checks that private read/send never calls ExecuteFunc or
changes shared scanner/fragment state; the observer alone can validate the packet
sequence, corrupt file content is rejected after synchronization, and concurrent
senders and export/readback retain identical shared state. Model passes are not
multiplayer engine acceptance. Retest `-loadf dev` in a fresh multiplayer PAIR010;
report the last loading message if it fails. PAIR008/PAIR009 stopped at classic source-agreement gates and are internal intermediates,
not the recommended candidate. Classic imported-character checkpoints remain a
separate unresolved engine test.

After multiplayer acceptance, apply the performance-audit fixes in separate
reviewable steps: release projectile hit tracking after impact/expiry; reclaim
save intermediates without dropping active sessions/screenshot codes; cache UI
handles with panel-open/load invalidation; and cache collection counters with
invalidation on addition/removal/import. The user's requested order is desync
first, then these improvements. None of those gameplay/performance changes is
included in the private-IO candidate.

PAIR010 validation: native 110 tests, classic 202 tests (8 skipped), all compiler,
content, source agreement, startup, save compatibility and conversion gates passed.
The separate focused suites passed: bounded/local IO 16, transport 23, paired
builder 19, save port 7. Both published files were copied to the Warcraft TEST
folder and hashes verified. Multiplayer engine confirmation is still pending.


### PAIR010 acceptance and PAIR011 cleanup

The user confirmed PAIR010 Forsaken multiplayer loading no longer desynchronizes.
A later three-player quest session froze after about four quests. PAIR011 adds
bounded save-fragment reclamation alongside the separate projectile/UI/collection
maintenance described in PERFORMANCE_AUDIT.md; multiplayer freezing acceptance is
still pending. No save format, item/job IDs or profile compatibility rules change.

Persistent virtual strings are rooted across module boundaries, including active
plans, result buffers and retained screenshot/file codes. New or unrooted fragments
are queued for later collection; each timer turn processes a fixed maximum per
arena. Shared and private roots, counters and queues remain separate, and no local
collector creates handles or enters shared validation. Collection runs between
non-yielding event stacks so temporary local aliases remain valid during a call.
Repeated round trips and interleaved concurrent senders run with collection enabled.
The sender releases its private code after its final packet; export readback checks
both body equality and the expected checksum header. Compiler/content/source/save
compatibility gates still apply to both output profiles.

The classic large-import Warcraft-menu checkpoint failure is not yet resolved.
Use new Warcraft checkpoints for engine retesting; existing checkpoints embed their
original map code. A successful import or small-profile checkpoint does not establish
large-profile checkpoint compatibility.
