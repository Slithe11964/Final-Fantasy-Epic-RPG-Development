# Early-story versus Kalm/Gilgamesh cinematic audit

Read-only audit, 2026-10-29. Compared packaged UI62 and native 0.9.7.5e
Hotfix10, including their editor modules and playable helpers. Both branches
have identical scene implementations for the six compared modules. The new
UI63 / Hotfix11 candidate does not change these scenes.

**Result:** meaningful differences exist, but no proven native crash cause or
direct client-dependent gameplay branch was identified. Mixed player reports
do not confirm a fix. Reports without exact map versions and crash stacks
cannot establish whether they exercised the current portrait workaround or the
same failure. The displayed ACCESS_VIOLATION text alone is not a stack match.

## What is already shared or changed

All six use Cine_Enter / Cine_ExitAction. Cine_Enter enumerates and pauses a
snapshot of existing eligible units, hides the interface and changes camera
state. Cine_Exit ends the portrait scene, restores the interface/camera and
unpauses that snapshot. All modules have matching static enter/exit counts.
None of the six modules directly branches on GetLocalPlayer; the shared exit's
local work is hero selection/camera restoration. This is not an exhaustive
proof about every transitive gameplay helper.

Historically, Kalm used null-speaker transmissions which still requested
SetCinematicScene(0). Mid/Ao mostly passed real speakers. UI59 / native Hotfix07
and later removed that rawcode-zero path and bypassed portrait, speaker ping
and unit-indicator rendering for every Kalm/Gilgamesh dialogue call. Normal
valid-speaker early story portraits remain. World unit models are still drawn.
Current Kalm/Gilgamesh failures cannot automatically be blamed on a portrait
call which this version no longer makes.

## Remaining leads, ranked by reported crash timing

1. **At Gilgamesh summon, before dialogue:** boss/unit/equipment creation and
   assets remain more relevant than dialogue. Summon creates N0LU and equips
   I011/I0DN/I0DO/I0DP/I00G/sror. Creation/equip events can run other systems.
   Later phases revive the same hero, remove and add equipment, register death
   events, and cast support spells. Audit those paths separately from opening
   captions; replacing dialogue does not cover them.
2. **Kalm transition/fade or “For our families!”:** Spawn_KalmDefenders hides
   recruited allies and builds/equips defenders. Completed quests choose extra
   cleric, golem, brothers, friends and support units. Two parties can therefore
   enter materially different spawn/equipment/asset branches. This is a concrete
   reason to investigate differences between reports, not proof of a fault.
3. **Opening conversation before defender rebuilding:** spawning later in the
   quest does not explain this point by itself. Check exact map identity,
   current actor models/effects, shared cinematic/UI lifecycle and actual dump.
4. **Overlapping scenes and waits:** Cine_Enter returns early when already in a
   scene, but does not give its callers an ownership result; those callers can
   continue and later invoke Cine_ExitAction. Kalm Begin timers explicitly defer
   while cinematic-busy; this is not a general queue/ownership mechanism for all
   scene callers. Timers continue through waits, and pausing units is not the
   same as pausing every timer. Potential interleaving remains a review lead;
   the early scenes share the same helper limitation.
5. **After phases, cleanup or exit:** Kalm has more kill/remove/revive work than
   Ao dialogue. Gilgamesh cleanup kills/removes the tracked boss and later
   encounters reuse its trigger machinery. Need a trace proving which lifecycle
   occurred before changing it. Existing local exit dumps implicate rendering
   container cleanup but do not identify one JASS call as the cause.

No new speculative cinematic patch was added with this audit. Next controlled
comparison should hold map version/client graphics fixed and distinguish:
opening dialogue, fade/defender rebuild, first boss creation, phase swap,
encounter cleanup, versus leaving the map. Compare parties with different
recruited allies and preserve actual Crash.txt/dumps for any failure.
